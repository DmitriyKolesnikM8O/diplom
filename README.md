# Первичный анализ темы ВКР

## Что есть на рынке; в какую нишу хочется целится; почему open source

### Существующие решения (беглый анализ)

1. **Промышленные антивирусные платформы и SDK (Enterprise)**
Представители: Kaspersky Scan Engine / KATA (и прочие коммерческие флагманские продукты), ReversingLabs Titanium Platform (Spectra Core), CrowdStrike Falcon (Static Core).

Особенности: Каждое это решение в своей сути - комплексное и многоуровневое, в которое "упихано" много всего: структурный разбор, эмуляция, проверка по облачным репутационным базам, ML-классификаторы, возможности интеграции с другими продуктами компаний. То есть это "сложные" и тяжеловесные решения, нередко компании "продают" экспертизу по их развертыванию и настройке. Плюсом такое вряд-ли подходит для обычных людей, это корпоративный сегмент, причем ориентированный на большие компании.

Ограничения:

  - Закрытость: Вся логика работы скрыты, это в полной мере black box;
  - Инфраструктурная связанность: Решения часто завязаны на тяжелый внутренний контур вендора (лицензионные серверы, базы метаданных, облачные репутации) и не могут работать как изолированная микроутилита;
  - Стоимость: развертывание, поддержка и обслуживание - недешевые вещи.

2. **Утилиты ручного анализа и триажа (Freeware / GUI)**

  - **pestudio (Marc Ochsenmeier)**:

Популярный инструмент для первичного ручного анализа PE-файлов в SOC-командах (проверка контрольных сумм, энтропии, оверлеев, TLS Callbacks, импортов).

Ограничения: Исходный код полностью закрыт. Бесплатная версия жестко ограничена графическим интерфейсом: консольный режим (CLI) и выгрузка отчетов в машиночитаемом виде (XML/JSON) заблокированы и доступны исключительно в коммерческой лицензии pestudio Pro. То есть тот же black box с невозможностью изменения + платно.

  - **PE-bear (hasherezade)**:

Еще один популярный инструмент для визуального исследования поврежденных и упакованных PE-структур. Вроде как даже open source и бесплатный соответственно.

Ограничения: Проект спроектирован исключительно для интерактивной работы человека через Qt GUI. В нем отсутствует headless-режим для поточной автоматизации, CI/CD-пайплайнов и генерации структурированных вердиктов (нельзя выгрузить отчет о структуре PE, импортах или аномалиях в машиночитаемом формате для последующего разбора скриптами). Еще и CLI ограниченный (Единственное, что можно сделать через командную строку — это передать путь к файлу при запуске, чтобы он сразу открылся в графическом окне приложения).

3. **Низкоуровневые открытые библиотеки разбора (Parsers)**

Представители: pefile (Python), LIEF (C++ / Python):

Библиотеки для прямого программного чтения и модификации полей PE/ELF/Mach-O форматов.

Ограничения: Это парсеры, а не аналитические системы. Они отображают внутренние структуры данных «как есть», не предоставляя встроенных эвристик, проверки корректности по спецификации Microsoft PE/COFF, расчета комплексных аномалий и скоринга рисков.

4. **Специализированные Open-Source детекторы**

  - **Detect It Easy (DiE):**

Быстро определяет упаковщики, протекторы и компиляторы.

Ограничения: Построен на байтовых сигнатурах и скриптах сопоставления шаблонов (при этом вроде как доступ к распарсенной структуре PE есть). DiE не ставит задачей проверку семантической целостности PE-заголовков относительно логики загрузчика Windows (ntdll!LdrLoadDll).

  - **Mandiant capa**:

Детектирует вредоносные возможности (capabilities) на основе открытых правил.

Ограничения: Требует полного дизассемблирования исполняемого кода и реконструкции графа потока управления (бэкенды SMDA, Vivisect, Ghidra). Анализ файла занимает много времени (до десятков секунд).

  - **Manalyze (JusticeRage)**:

C++ статический анализатор с плагинной архитектурой.

Ограничения: Вроде отстал от современности и давно не разрабатывается активно, хотя какие-то PR в проекте есть. Инструмент не учитывает современные техники модификации PE.

### В какую нишу хочется целится

Хочется метить в разработку компактного, автономного инструмента первичного структурного триажа.

Какие проблемыв  автоматизированном первичном анализе исполняемых файлов кажутся актуальными:
1. **Проблема расхождения парсеров:**
   Многие стандартные статические анализаторы ориентируются на идеальное соблюдение формата PE и завершают работу с ошибкой при встрече с намеренно деформированными заголовками.
   - хочется решать задачу моделирования поведения загрузчика с явным детектированием попыток сломать парсинг (Malformed PE).

3. **Отсутствие открытых автономных решений для автоматизации:**
   Многие инструменты либо требуют лицензию для работы в режиме командной строки и выгрузки JSON (pestudio), либо привязаны к графическому интерфейсу (PE-bear), либо заброшены разработчиками (Manalyze). В открытом доступе отсутствует современный модульный инструмент первичного скоринга аномалий, готовый к интеграции в CI/CD и скрипты автоматизации.

4. **Снижение вычислительной нагрузки на конвейеры анализа:**
   Глубокий анализ в песочницах и дизассемблерах требует вычислительных ресурсов.
   - хочется закрыть потребность в легковесном фильтре первого эшелона, позволяя относительно быстро классифицировать файл по уровню структурной аномальности без перехода к тяжелому анализу машинного кода.

Что видится реальным добавить в проект:

  - Спецификационный аудит (Compliance Check): Проверка структуры PE на соответствие официальной спецификации Microsoft и логике загрузчика Windows (ntdll!LdrLoadDll). Выявление намеренно некорректных полей, вызывающих падения у стандартных парсеров.
  - Детекция структурных аномалий: Алгоритмический поиск манипуляций с OptionalHeader, аномальных смещений секций, расхождений между виртуальным и сырым размером, наличия оверлеев и модификаций Rich Header.
  - Энтропийный профиль: Расчет энтропии по скользящему окну для выявления упакованных фрагментов и скрытых пейлоадов без полного запуска файла.
  - Интерфейс: Автономный консольный интерфейс (CLI) с экспортом результатов в структурированный JSON для встраивания в сторонние скрипты.

Что кажется логичным пока отложить (так как видится сложным):

  - Дизассемблирование машинного кода и эмуляция инструкций.
  - Использование облачных сервисов или закрытых баз знаний (интеграции или возможности предоставления интеграций со сторонними решениями).

Ну то есть хочется получить на выходе прозрачный, расширяемый Open-Source инструмент и модуль, который любой исследователь или студент может запустить локально, изучить логику каждого правила и встроить в собственный конвейер анализа.

### почему open source

Хочется создать именно открытый инструмент, что-то вроде "ядра", которое каждый может взять без лицензий, изменить и доработать для себя; ну либо просто обвязку сделать. 
Также это даёт независимость от корпоративной инфраструктуры, исключает конфликты с коммерческой тайной и NDA.

Очень перекликается идея с такой популярной в мире ИБ штукой, как Suricata. Это полностью бесплатный open source проект - IDS движок, который не является закрытым комбайном со всем, а целится в быструю инспекцию по правилам. Крупные компании берут это себе, строят вокруг него логику, обвязки, ну либо просто интегрируют в свои проекты. Идея близка. 

## Цель, задачи

### Цель работы
Разработка открытого программного инструмента первичного статического анализа исполняемых файлов формата PE для выявления структурных аномалий, деформаций формата (Malformed PE) и техник сокрытия данных с учётом особенностей системного загрузчика Windows.

### Задачи (ориентировочные)

1. **Исследование предметной области и систематизация аномалий формата:**
  - провести анализ спецификации Microsoft PE/COFF и механизмов сопоставления структур системным загрузчиком Windows
  - исследовать расхождение парсеров, возможно составить классификацию техник структурной эвазии (когда файлик меняют как-то, чтобы антивирусы и прочее не обнаружило)

2. **Разработка алгоритмов структурного анализа и эвристик:**
  - спроектировать  алгоритмы валидации полей заголовков на устойчивость к намеренным искажениям без аварийного завершения работы парсера
  - разработать алгоритмические правила выявления признаков сжатия, упаковки и обфускации структуры исполняемого файла
  - реализовать логику классификации файлов по уровню риска на основе критичности обнаруженных аномалий

3. **Проектирование и программная реализация инструмента:**
  - спроектировать модульную архитектуру независимого аналитического ядра с безопасной работой с памятью
  - реализовать консольный интерфейс (CLI) для автономной работы в изолированных средах
  - реализовать механизм сериализации результатов анализа в машиночитаемый формат JSON для интеграции инструмента в сторонние конвейеры обработки (CI/CD, брокеры сообщений).

4. **Формирование тестовой выборки и валидация:**
  - подготовить набор тестовых файлов (чистые системные программы и образцы с аномалиями) для проверки работы программы
  - Провести экспериментальное тестирование инструмента на устойчивость к сбоям при обработке некорректных структур данных.

5. **Сравнительный анализ и оценка эффективности:**
  - наверное надо сравнить с тем, что есть сейчас в нише
  - оценить полноту детекции структурных аномалий и вычислительную производительность (первое, что приходит на ум: время обработки одного файла).
