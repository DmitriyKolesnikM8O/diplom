# Архитектура `peaudit`

> Черновик. Полное описание появится по мере прохождения фаз 2–5
> (см. [`materials/roadmap.md`](../materials/roadmap.md)).

## Слои

```
peaudit-core   парсинг PE, модель, правила, скоринг, отчёт
peaudit-cli    аргументы, ввод-вывод, коды возврата
peaudit-ffi    C ABI (cdylib/staticlib)
xtask          служебные команды (ci, corpus, experiment, schema)
```

Зависимости направлены только внутрь: `cli`/`ffi` → `core`; `core` не знает
про файловую систему, CLI и FFI.

## Принципы

- zero-copy разбор по `&[u8]`;
- проверка границ на каждом чтении, никаких паник на входных данных;
- partial parsing: ошибка фиксируется как диагностика, анализ продолжается
  ([ADR-0003](adr/0003-partial-parsing.md));
- детерминированный отчёт;
- лимиты на число секций, директорий, импортов, узлов ресурсов и глубину рекурсии;
- три независимых профиля вердикта — `spec`, `loader`, `security`
  ([ADR-0004](adr/0004-three-profiles.md));
- `#![forbid(unsafe_code)]` в ядре.

## Модули ядра

```
bytes     Reader: zero-copy чтение с проверкой границ, peek/slice/sub_reader
derived   Derived: производные величины — HeadersSize, ImageSize, OverlayInfo, ChecksumInfo,
          SectionEntropy
error     ParseError, Diagnostic, DiagCode — ошибки как данные, без аллокаций
codes     реестр стабильных кодов диагностики (единственное место создания кодов)
limits    safety-лимиты: потолки на объём работы и памяти
spec      пороги спецификации PE/COFF (96 секций, 16 директорий, глубина 3)
pe        заголовки DOS/COFF/optional/секции и PeFile::parse (partial parsing)
pe::rva   перевод RVA в файловое смещение: spec / loader / max-virtual-raw
pe::overlay  разбиение данных после образа: leading / certificate / trailing
pe::checksum PE checksum: сумма слов с маскированным полем плюс длина файла
hash      SHA-256, SHA-1, MD5; по умолчанию считается только SHA-256
entropy   энтропия Шеннона и скользящее окно
testutil  PeBuilder: синтетические PE32/PE32+ с патчами полей (для тестов и xtask)
```

`pe` — единственное место, где байты превращаются в модель. Порядок разбора
жёсткий (DOS → подпись `PE\0\0` → COFF → optional → директории → секции), а
реакция на ошибку — нет: каждая неудача становится диагностикой, и разбор
продолжается с того, что ещё достижимо. Поэтому `PeFile` состоит из
`Option`-полей, а `ParseState` говорит лишь о том, **как далеко** прошёл
парсер, но не о валидности файла. `Complete` означает «разобрано всё
объявленное»; файл без секций разбирается полностью и всё равно некорректен —
это находка правила, а не ошибка парсера.

Таблица секций ищется по объявленному `SizeOfOptionalHeader`, а не по
фактически разобранному размеру: так же поступает загрузчик Windows, и
именно расхождение этих величин даёт parser differential.

**Директории и секции ограничиваются по-разному, и это осознанно.** Каталог
директорий читается не более 16 записей — дальше загрузчик их не смотрит, и
любые «лишние» байты на месте 17-й записи на самом деле уже таблица секций.
Секции, наоборот, читаются до safety-лимита даже за порогом спецификации (96):
анализатору нужно показать их все, а нарушение сообщит правило
`PE-COFF-001`. Такое расхождение зафиксировано ещё и диагностикой
`optional.too-many-directories`: модель содержит меньше объявленного, и отчёт
обязан это объяснить.

**Диагностика — не находка** ([ADR-0005](adr/0005-diagnostics-vs-findings.md)).
Диагностика фиксирует **решение парсера**: он остановился раньше, урезал
счётчик, пропустил подструктуру — то есть модель отличается от того, что
объявлено в файле. Аномалия, не требующая решения (ноль секций, значение вне
спецификации), диагностики не порождает: она точно представлена в модели, а
соответствие спецификации оценивает правило. Поэтому усечение любой структуры —
всегда уровень `error` (иначе `complete` перестаёт быть правдой), а реестр
кодов не содержит заготовок: каждый код производится каким-то входом, и это
проверяется тестом.

**Один RVA — три честных ответа.** Перевод RVA в файловое смещение не имеет
единственно верного правила на краях: спецификация, загрузчик и сторонние
парсеры расходятся, и malformed-файлы живут именно в этих расхождениях. Поэтому
`pe::rva` реализует три стратегии (`Spec`, `Loader`, `MaxVirtualRaw`) и умеет
возвращать все три ответа сразу (`resolve_rva`), чтобы правило могло показать
расхождение, а не спрятать его за выбором по умолчанию. Внутри секции
результат — это либо файловое смещение, либо `ZeroFill` (хвост
`VirtualSize > SizeOfRawData`), либо `Unmapped`. Функции не смотрят на длину
файла: «смещение за концом файла» — находка правила `PE-SEC-001`, а не повод
изменить маппинг. Иначе нельзя отличить маппинг, который ведёт за конец файла,
от ошибки в самом маппинге. При пересечении секций побеждает первая по
таблице — эта зависимость от порядка и есть то, что отчёт обязан показать.

**Производные величины отделены от разбора.** `Derived::compute` отвечает на
вопрос «что следует из объявленного»: `HeadersSize` (сколько занимают
заголовки и покрывает ли их `SizeOfHeaders`) и `ImageSize` (совпадает ли
`SizeOfImage` с `align_up(max(VA + VirtualSize), SectionAlignment)`). Парсер
при этом ничего не оценивает: он сообщает числа, а сравнение и вердикт — дело
правила (`PE-OPT-002`, `PE-OPT-003`), поэтому в отчёт попадают оба значения, а
не только факт «не сходится». Величина, которую нельзя вычислить (нет optional
header, нет секций, нулевое выравнивание), — `None`, а не диагностика: файл
просто в таком состоянии, что вопрос не имеет смысла. Конец заголовков
считается по **объявленному** числу секций, а не по числу прочитанных: загрузчику
нужно место под каждую объявленную запись, а усечённая таблица сообщается
отдельно (`sections.truncated`).

**Overlay — это не «всё после последней секции».** `pe::overlay` делит хвост
файла на три региона: `leading` (данные до таблицы сертификатов), `certificate`
(сама таблица — только если она начинается не раньше конца секций) и `trailing`
(данные после подписи, T44/`PE-CERT-002`). Одна пара `(offset, size)` не
описывает все случаи: подпись — легитимное дополнение, из-за которого наивное
правило даёт ложное срабатывание, а данные после неё — уже сокрытие. Каталог
сертификатов — единственный, чей `VirtualAddress` является файловым смещением,
а не RVA; его размер обрезается по концу файла, а каталог, начинающийся раньше
секций, не вычитается из overlay: он перекрывает образ, и это отдельная
находка, а не повод придумывать разбиение. Overlay никогда не начинается
внутри заголовков — старт равен максимуму из конца raw-данных секций, конца
объявленной таблицы секций и `SizeOfHeaders`, иначе байты заголовков попали бы
в «данные после образа».

**Checksum считается так же, как в Windows.** `pe::checksum` — сумма 16-битных
little-endian слов плюс длина файла, с обнулением четырёх байт самого поля:
поле маскируется, а не пропускается по индексу слова, иначе у невыровненного
поля в соседних словах остались бы чужие байты. Нечётный последний байт
складывается как слово с нулевой старшей половиной. Значение `0` означает «не
задано» — линкер заполняет поле только для образов, которые будут проверяться, —
и расхождением не считается. Алгоритм закреплён векторами от системного
`MapFileAndCheckSumW` (`imagehlp.dll`): PE32-фикстура `0x9205`, PE32+ `0x36EF`,
`notepad.exe` `0x618DE`; собственной реализацией векторы не порождаются.

**Энтропия считается один раз.** `Derived::section_entropy` содержит по записи
на каждую разобранную секцию: обрезанный по файлу диапазон, энтропию Шеннона по
**присутствующим** байтам и признак `truncated` (файл короче объявленного raw).
Именно по присутствующим, а не по `VirtualSize`: нулевой хвост создаёт загрузчик,
и его «энтропия» ничего не говорит о данных. Правило, решающее «секция
упакована», не должно сканировать файл само — иначе два правила посмотрят разные
диапазоны и разойдутся. При этом энтропия — сигнал, а не вердикт: на 6 058
секциях `System32` 15 имеют ≥ 7.0 бит/байт (сжатые ресурсы), поэтому
`is_high_entropy` сама по себе находкой быть не может.

**Хэши — не бесплатные.** Каждый дайджест — полный проход по файлу. На 10 МиБ
один SHA-256 стоит ≈ 9 мс, а все три — ≈ 47 мс (в 5.5 раза дороже), поэтому
по умолчанию считается только SHA-256; SHA-1 и MD5 включаются флагом
`--hashes all` для сверки с внешними базами. Замер —
`docs/experiments/2026-11-22-hash-baseline.md`.

**`limits` и `spec` — разные вещи.** `spec` содержит значения, заданные
спецификацией; их превышение — находка правила, а не повод прекратить разбор.
`limits` содержит только потолки безопасности; их превышение — диагностика
`LimitExceeded` и пропуск затронутой подструктуры. Смешение двух смыслов
привело бы к потере улик в повреждённом файле и к ложным «limit exceeded» на
легитимных файлах.

## Поток данных

```
байты → Reader → PeFile → Derived (RVA, overlay, checksum, энтропия)
      → AnalysisContext → правила → Finding[] → скоринг → Report → JSON
```

Подробности и обоснование решений — в roadmap и ADR (`docs/adr/`).
