# Производные величины на корпусе: RVA, размеры, overlay, checksum

- **Дата:** 2026-11-24
- **Фаза:** 4 (производная модель)
- **Платформа:** Windows 11, Rust 1.99.1, профиль `release` (для времени), `dev` (для сверки)
- **Корпус:** `C:\Windows\System32`, расширения `.exe`, `.dll`, `.sys`

## Что проверялось

Производные величины — это утверждения о файле, которые нельзя проверить
чтением одного поля: «этот `SizeOfImage` описывает ровно то, что лежит в
таблице секций», «эта подпись не является overlay», «эта контрольная сумма
посчитана по этим байтам». На реальных файлах Microsoft они обязаны сходиться,
поэтому корпусный прогон отвечает на пять вопросов:

1. Покрывает ли объявленный `SizeOfHeaders` фактический конец таблицы секций.
2. Совпадает ли объявленный `SizeOfImage` с `align_up(max(VA + VirtualSize), SectionAlignment)`.
3. Встречаются ли overlay и встроенные подписи, и не путает ли разбиение одно с другим.
4. Совпадает ли сохранённый checksum с вычисленным там, где он вообще задан.
5. Целиком ли лежат raw-данные секций в файле и насколько высока энтропия
   на легитимных образах — иначе непонятно, с чем сравнивать правило про
   упакованные секции.

```powershell
$env:PEAUDIT_SYSTEM_CORPUS = "C:\Windows\System32"
$env:PEAUDIT_CORPUS_LIMIT = "1000"
cargo test -p peaudit-core --test system_corpus --release -- --ignored --nocapture
```

Профиль `release` здесь не для красоты: checksum — полный проход по файлу, и в
`dev`-сборке прогон 1000 файлов занимает ≈ 55 с против ≈ 2 с в `release`.

## Результат

| Проверка | Значение | Расхождений |
|---|---|---|
| Файлов разобрано | 1000 (`complete` — 1000) | — |
| Секций / директорий | 6 058 / 16 000 | — |
| `SizeOfHeaders` покрывает таблицу | 1000 из 1000 | 0 |
| `SizeOfImage` = вычисленный | 1000 из 1000 | 0 |
| Overlay (`leading` + `trailing`) | 0 файлов | — |
| Встроенная таблица сертификатов | 149 файлов | — |
| Секции с усечёнными raw-данными | 0 из 6 058 | — |
| Секции с энтропией ≥ 7.0 бит/байт | 15 из 6 058 | — |
| Checksum задан (не `0`) | 999 из 1000 | 0 |

- **Размеры сходятся на всех файлах.** Ни одного файла, где `SizeOfHeaders` не
  покрывает таблицу секций или `SizeOfImage` не равен вычисленному: значит,
  пороги правил `PE-OPT-002`/`PE-OPT-003` на легитимном корпусе молчат, а
  срабатывание на них — сразу сигнал о дефекте правила, а не о файле.
- **149 подписей — и ни одного overlay.** Разбиение вокруг certificate table
  проверено на реальных данных, а не только на синтетике: у всех 149 файлов
  таблица сертификатов начинается ровно в конце raw-данных секций и
  заканчивается ровно в конце файла, поэтому `leading` и `trailing` пусты, а
  `is_present()` возвращает `false`. Наивное правило «всё после последней
  секции — overlay» дало бы 149 ложных срабатываний на 1000 файлов (15 %).
- **`overlay` в `System32` нет** — это ожидаемо и является baseline: появление
  overlay на системном файле означает либо обновление, либо вмешательство.
- **999 checksum из 1000 совпали.** Один файл хранит `0` — «не задано»;
  трактовать это как расхождение было бы ложным срабатыванием. Остальные 999 —
  точное совпадение с независимой реализацией Windows (см. ниже).
- **Ни одна секция не усечена.** Raw-данные всех 6 058 секций целиком лежат в
  файле: это baseline для `PE-SEC-001`, любое срабатывание на системном файле —
  повод проверить правило.
- **Энтропия ≥ 7.0 бит/байт у 15 секций из 6 058 (0.25 %).** Это сжатые ресурсы
  (`.rsrc`), а не упакованный код: высокая энтропия сама по себе не может быть
  находкой, правило обязано добавлять контекст — имя и флаги секции, долю
  файла, наличие кода.

## Сверка checksum с Windows

Векторы получены не из собственной реализации, а от системной функции
`MapFileAndCheckSumW` (`imagehlp.dll`), которая используется Windows при
проверке образов:

| Вход | stored | computed |
|---|---|---|
| фикстура `PeBuilder::pe32` (1024 байта) | `0x00000000` | `0x00009205` |
| фикстура `PeBuilder::pe32plus` | `0x00000000` | `0x000036EF` |
| `C:\Windows\System32\notepad.exe` | `0x000618DE` | `0x000618DE` |
| `C:\Windows\System32\drivers\disk.sys` | `0x0001E1B2` | `0x0001E1B2` |

Первые две строки закреплены unit-тестом `pe::checksum::tests::windows_vectors_match`;
последние две — ручная сверка. `disk.sys` заодно показывает разбиение overlay:

```
overlay: leading = None certificate = Some(DataRegion { offset: 114688, size: 8520 }) trailing = None
checksum: stored = Some(1e1b2) computed = Some(1e1b2) set = true consistent = Some(true)
```

114688 + 8520 = 123208 — ровно длина файла.

## Вывод

- Производная модель на реальном корпусе не даёт ни одного расхождения: правила
  фазы 5 могут опираться на неё как на baseline, а любое срабатывание на
  системном файле — сначала повод проверить правило.
- Overlay и certificate table необходимо разделять до того, как появится первое
  правило: иначе 15 % корпуса выглядят подозрительными.
- Стоимость checksum — один полный проход по файлу (≈ 2 мс на файл вместе с
  чтением с диска в `release`); в отчёт это значение попадает всегда, потому что
  дешевле, чем любая эвристика вокруг него.
- Энтропия по секциям — второй такой же проход, но считается один раз при
  разборе и переиспользуется всеми правилами. Итог: 2.3 с на 1000 файлов в
  `release` (три прохода: чтение, checksum, энтропия).

## Ограничения

- Только образы Microsoft из одной установки Windows: нет packed-файлов, нет
  Corkami-поделок, нет файлов с настоящим overlay. Путь `leading`/`trailing`
  проверен unit-тестами и синтетикой (`PeBuilder` + хвост байт).
- Корпус не входит в репозиторий и в CI; прогон ручной, под `--ignored`.
- 1000 файлов — выборка, а не весь `System32`: правило, зависящее от редкой
  раскладки, на ней может не проявиться.
