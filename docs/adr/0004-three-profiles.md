# ADR-0004. Три профиля: spec, loader, security

- **Статус:** принято
- **Дата:** 2026-11-22
- **Связано:** ADR-0003 (partial parsing), `materials/roadmap.md` §4.7, `materials/evasion-taxonomy.md`

## Контекст

Один и тот же PE-файл отвечает на разные вопросы по-разному:

- **Соответствует ли он спецификации Microsoft PE/COFF?** Хвостовые пустые секции,
  `VirtualSize < SizeOfRawData`, `LoaderFlags != 0` — нарушения.
- **Примет ли его загрузчик Windows и отработает ли без сбоя?** Те же хвостовые
  секции загрузчик принимает, а `e_lfanew` за `SizeOfHeaders` — отвергает.
- **Есть ли признаки намеренного сокрытия?** Пустые секции, маскировка имён,
  высокоэнтропийный overlay — типичные трюки, даже если файл загружается.

Свести это к одному числу или одному вердикту нельзя: файл может быть
невалидным по спецификации, но полностью рабочим, и наоборот — валидным, но
подозрительным. Именно этот зазор и эксплуатируется (см. таксономию).

## Решение

1. **Три независимые семантические модели**, а не «уровни строгости»:

   | Профиль | Вопрос | Пример |
   |---|---|---|
   | `spec` | Соответствие спецификации PE/COFF | `SizeOfRawData` не кратен `FileAlignment` → нарушение |
   | `loader` | Примет ли загрузчик и отработает ли без сбоя | Хвостовые пустые секции → не находка |
   | `security` | Структурные аномалии и признаки сокрытия | Хвостовые пустые секции → находка |

2. **Один проход анализа, все правила выполняются всегда.** Каждое правило имеет
   `RuleMeta.profiles` — набор профилей, в которых его находка учитывается.
   Фильтрация по профилю не меняет набор выполнимых проверок, а значит, отчёт
   остаётся детерминированным и полным.

3. **Отчёт всегда содержит все три вердикта**, независимо от `--profile`.
   Профиль влияет только на:
   - какой вердикт используется для `--fail-on` (по умолчанию `security`);
   - что показывать в human-выводе по умолчанию (JSON не фильтруется).

4. **Профиль — не то же самое, что severity.** Severity — свойство находки
   (насколько она серьёзная), профиль — принадлежность к модели (кого она
   касается). Находка `PE-LDR-001` может быть `medium` по severity и одновременно
   отсутствовать в профиле `spec`, потому что спецификация такого случая не
   описывает.

5. **`--fail-on` работает по severity отдельной находки выбранного профиля**, а не
   по score. Причина: порог по severity объясним и стабилен в CI, тогда как score
   калибруется на корпусах и может меняться между версиями.

## Последствия

**Положительные.**

- В отчёте видно *расхождение моделей*, а не усреднённая оценка: «валиден по
  спецификации, но загрузчик откажет» — это готовый вывод для главы 1 и для
  исследователя.
- Профили напрямую соответствуют колонкам таксономии, что упрощает защиту работы:
  каждая колонка таблицы техник — это отдельный профиль.
- `--fail-on` можно настроить под задачу: CI самого инструмента, проверка
  соответствия или триаж образцов.

**Отрицательные.**

- Пользователю нужно объяснить три вердикта; human-вывод должен быть явным, иначе
  «три статуса» читаются как противоречие.
- Каждое правило требует осознанного выбора профилей при добавлении, иначе
  находка «пропадает» из нужной модели.
- Три вердикта нельзя сравнивать между собой числом; для сортировки нужен
  отдельный score, который живёт в профиле `security`.

**Риски и их снятие.**

- *Правило забыли пометить профилем.* Снимается тестом реестра: каждое правило
  обязано иметь непустой `profiles`, а CI проверяет, что все профили известны.
- *Профиль начали использовать как фильтр правил.* Зафиксировано в этом ADR:
  профиль не отключает проверки, он только выбирает вердикт для гейта.

## Альтернативы

1. **Единый score без профилей.** Проще для пользователя, но теряет главное —
   расхождение спецификации, загрузчика и эвристик. Отвергнуто.
2. **Уровни строгости (`lenient`/`normal`/`strict`).** Смешивают два измерения
   (полнота разбора и семантика проверки) и не отвечают на вопрос «загрузится ли».
   Отвергнуто; `lenient`/`strict` остались только как режим парсера (ADR-0003).
3. **Три отдельных прогона с фильтром по профилю.** Тройная работа, тройной вывод
   и риск расхождения между прогонами. Отвергнуто.
4. **Профиль как единственный вердикт в отчёте.** Пользователь не увидит
   расхождений, ради которых всё делается. Отвергнуто.
